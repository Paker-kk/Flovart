Flovart is a local-first AI creation system with three distinct workspaces: Workflow, Table, and Agent.

## Creative workspaces

| Workspace | Responsibility | Current status |
| --- | --- | --- |
| **Workflow** | Orchestrates prompts, references, generation models, node dependencies, job state, and results for image and video production. | A usable foundation exists; interaction and runtime contracts are still converging. |
| **Table** | Organizes agent storyboards and media preprocessing nodes that turn source media into reusable references. | The official entry point is integrated; the node workbench is still a placeholder. |
| **Agent** | Acts as the production-crew control surface for Director Bindings, execution state, approvals, receipts, context, and artifacts. | The target architecture is designed; the current built-in-main-agent implementation still needs migration. |

The removed Canvas and Art workspaces are not a fourth product surface.

## Workflow

- Compose image, text, video, audio, and configuration nodes into generation flows.
- Use PromptBar to select product models, generation modes, parameters, and references.
- Connect nodes, switch local projects, drop local media, monitor generation, stop work, and receive result nodes.
- Reuse characters, scenes, props, and generated artifacts from the local asset library.
- The current CLI registry exposes Workflow project, node, connection, viewport, run, and stop commands.
- The target AI-native record surface combines the canvas's current state with a semantic ChangeSet timeline; chat carries intent and explanation, not the sole operation history. This remains planned work and must not be presented as complete.

## Table

Table is neither a spreadsheet nor a rename of the old Canvas. It is planned around two progressively disclosed node groups:

- **Agent storyboard**: brief, sequence, scene, shot, and storyboard cards that an Agent Skill can draft, decompose, and revise.
- **Media preprocessing**: image or video inputs, subject cutout, depth images and depth videos, edge/line-art/normal/pose extraction, stylization and glitch filters, plus source preparation for wardrobe edits and omni-reference generation.
- **Artifact handoff**: preserve provenance, save results to the asset library, and use them as Workflow references.

Workflow and Table are separated by interaction complexity: Workflow may keep single-step, local operations that directly serve the generation chain, while batch, multi-step, multi-input/output, timeline-precision, and reusable processing pipelines belong in Table. They may share operation schemas and executors, but never graph-node instances or history.

When a single-step operation grows into a complex pipeline, an explicit Table Promotion transfers editing authority to a new Table Session. Workflow references only an explicitly published Artifact; Table experiments never overwrite Workflow through live bidirectional sync.

The main Table implementation is not complete. These planned capabilities must not be described as available until their nodes, persistence, and export paths are integrated. The current CLI has no Table commands.

## Agent

Agent is neither a Workflow chat drawer, a mirror of an external harness conversation, nor another generation graph. Its target form is a spatial production control surface with movable panels for Director Bindings, intents, status, approvals, Workspace Operator receipts, and artifacts. The canonical conversation, overall goal, and cross-task scheduling remain in the independently running External Coding Agent Harness. The current code still follows the older “built-in main Flovart Agent plus Codex subtasks” direction; its migration is listed in the [backlog](../progress/todo.mdx).

The product has exactly two AI roles: the external director harness and the single built-in Workspace Operator. Production Crew is only a group name for the Operator plus deterministic dispatch/runtime capabilities and provider workers; it is not a third agent. Even model-based expert review is a stateless one-shot Review Tool.

## CLI and external agents

- The External Coding Agent Harness is the director. Coding Agent Projections learn Flovart through an Operation Skill and call typed capabilities through the public CLI; the target public boundary provides no coding-agent MCP server. The internal MCP transport still present in the legacy Managed/Codex adapter is migration code scheduled for deletion, not a supported integration path.
- Codex is the current professional golden path; DeepSeek Harness keeps an explicit native Plugin projection; CodeBuddy Code, Claude Code, OpenCode, and Pi remain compatible through the stable Skill + CLI contract. WorkBuddy is a future mainstream, skill-mediated projection and is outside the current Director Binding scope.
- The target deep DeepSeek experience is a dedicated Flovart Profile with a Host/Client Plugin. DeepSeek Harness remains the application shell, canonical conversation, and default director; a fixed Flovart Dock opens the complete Workflow/Table/Agent Production Control surface in the central workspace, lightweight overlays handle approvals/status/artifacts, and the right-side Agent Bridge manages connections plus single-director handoff, with a standalone-window fallback. The Host still executes model tools through the CLI; the Client uses a scoped local channel only for UI, events, and recovery. This has not passed real installation and recovery acceptance and must not be presented as shipped.
- Flovart CLI is the deterministic actuator; `command.list` and `command.schema` are the source of truth for command names and options.
- The CLI may use a versioned local protocol internally, but external models do not consume it directly. Only the trusted DeepSeek Client Plugin may consume a short-lived, capability-scoped UI/event subset.
- Current automation is Workflow-first. A harness must not invent Canvas, Element, or Table commands or bypass the CLI with private HTTP calls.
- Users configure provider credentials; CLI and agent output must never read or expose API keys.

See the [Agent architecture design package](../../../design/agent/README.md) for the target, protocol boundary, migration plan, and acceptance gates.

## Local-first boundaries

- Workspace projects, assets, and generation history are currently stored mainly in the browser; cloud sync is not promised.
- API keys currently stay in browser storage, and the frontend calls configured model services directly.
- Flovart does not bundle model services. Users remain responsible for the rights and compliance of their inputs and generated output.
